La latence par token n'est pas une vitesse : c'est une distribution, et le nombre qui compte sur un système temps réel est son maximum, pas sa moyenne. Ce rapport donne la méthode, les chiffres mesurés, et la liste exacte de ce qui reste à mesurer.

Donc : des chiffres pessimistes. Une machine au repos de la même classe fait mieux. Nous publions les pessimistes parce que ce sont ceux dont nous avons les artefacts, et parce que les trois modèles ont été mesurés sous la même charge.

Méthode

  • Débit de génération / latence par token : llama-bench, -t 4 -p 512 -n 128, 5 répétitions ; max et p90 sur les échantillons par exécution.
  • Évaluation de prompt : llama-bench -p 512.
  • RAM résidente : ensemble résident du processus pendant la génération.
  • Latence par token : 1000 / (tokens par seconde).
  • Sur la cible : horodatage par token avec clock_gettime_ns(CLOCK_MONOTONIC) dans le thread d'inférence ; le noyau QNX 8.0 est sans tick, donc la mesure n'hérite d'aucune quantification d'horloge.

Limites, dites avant qu'on nous les demande

  • Sous émulateur, les durées absolues de la trace sont dilatées. La documentation SDP exige que ClockCycles() soit synchronisé entre les CPU pour que tracelogger produise des horodatages significatifs ; un émulateur ne le garantit pas. L'ordre des événements est solide ; les durées ne sont pas au niveau du silicium.
  • Aucun chiffre n'est extrapolé de l'hôte vers l'invité. L'invité sera plus lent (pas de GPU, émulateur, chemin mémoire différent) ; ses chiffres propres seront mesurés.
  • APS n'existe plus dans QNX 8.0 — la preuve d'isolation repose sur la priorité, l'affinité et la trace, pas sur un partitionnement par budget. Voir docs/QNX-SPECIFICS.md.
  • Les modèles à raisonnement noient la réponse sous leur trace de pensée ; il faut désactiver le raisonnement (enable_thinking=false) pour obtenir une réponse finale dans le budget de tokens.
